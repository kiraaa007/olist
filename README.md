# Olist E-Commerce Analytics & Late-Delivery Prediction

A Streamlit project for analyzing Olist e-commerce performance and predicting whether a delivered order is likely to arrive late.

The project combines two goals:

1. **Business analytics** — understand sales, orders, freight, delivery performance, customer reviews, category performance, geography, and retention.
2. **Machine learning** — use information available at order time to predict late-delivery risk with a Random Forest classifier.

---

## Business Context

Olist is an e-commerce marketplace dataset connecting customers, orders, products, sellers, payments, deliveries, and reviews.

This project answers business questions such as:

- How much product value is being sold?
- How many delivered orders are being processed?
- What is the average order value?
- How much of collected order value is related to freight?
- How long do deliveries take?
- What percentage of orders arrive late?
- Which categories and states generate the most sales?
- Which states and categories have the highest late-delivery risk?
- Are late deliveries associated with lower review scores?
- How many customers place more than one order?
- Can late orders be identified before delivery?

## Data Pipeline

The raw Olist data contains different grains. For example, one order can contain multiple item rows, payment rows, or review rows.

The project converts these raw tables into a single analytical dataset with:

> **One row per delivered order**

### Main preparation steps

1. Load the Olist source CSV files.
2. Remove duplicate order and dimension records.
3. Convert order timestamp columns to datetime values.
4. Keep only delivered orders with complete purchase, estimated-delivery, and actual-delivery timestamps.
5. Merge product-category translations and seller information into order items.
6. Aggregate all item rows to one summary row per order.
7. Aggregate repeated payment rows per order.
8. Aggregate repeated review rows per order.
9. Merge customers, items, payments, and reviews into the order-level dataset.
10. Engineer delivery, calendar, and target variables.
11. Validate that every `order_id` appears only once.

### Order-item aggregation

For each order, the project calculates:

- `item_count` = number of item rows
- `total_sales` = sum of item prices
- `total_freight` = sum of freight values
- `product_category` = deterministic most-common category
- `seller_state` = deterministic most-common seller state

If multiple categories or sellers are tied for the most common value, the code sorts the tied values and selects the first one so the result is reproducible.

---

## Engineered Variables

### Purchase month

```text
purchase_month = month(order_purchase_timestamp)
```

### Purchase period

A monthly period such as `2018-05`, used for the monthly revenue trend.

### Estimated delivery days

```text
estimated_delivery_days = estimated_delivery_date - purchase_date
```

### Actual delivery days

```text
delivery_days = actual_delivery_date - purchase_date
```

### Late-delivery target

```text
is_late = 1, if actual delivery date > estimated delivery date
is_late = 0, otherwise
```

An order delivered exactly on the estimated date is considered **On Time**.

# Business KPI Dashboard

All dashboard KPIs are calculated from the currently filtered delivered-order dataset. Filters are available for customer state and product category.

## 1. Revenue

```text
Revenue = Σ total_sales
```

`total_sales` is the sum of item prices, so this KPI represents product sales / merchandise value in the analytical dataset. Freight is not included in this KPI.

---

## 2. Total Orders

```text
Total Orders = COUNT DISTINCT(order_id)
```

Because the prepared dataset is one row per order, this represents the number of delivered orders in the current view.

---

## 3. Average Order Value (AOV)

```text
Average Order Value = Total Revenue / Total Orders
```

This measures the average product-sales value generated by one delivered order.

---

## 4. Total Freight

```text
Total Freight = Σ total_freight
```

This is the total freight value associated with all selected delivered orders.

---

## 5. Average Delivery Time

```text
Average Delivery = MEAN(delivery_days)
```

Where:

```text
delivery_days = actual delivery date - purchase date
```

This shows the average number of days from order purchase to delivery.

---

## 6. Late Rate

```text
Late Rate = Late Orders / Total Orders
```

The code calculates this as the mean of the binary `is_late` variable:

```text
Late = 1
On Time = 0
```

Therefore:

```text
MEAN(is_late) = Late Orders / Total Orders
```

### Delivery guardrail

- `Late Rate <= 10%` → within the project guardrail
- `Late Rate > 10%` → warning

---

## 7. On-Time Rate

```text
On-Time Rate = 1 - Late Rate
```

---

## 8. Average Review Score

```text
Average Review = MEAN(average_review_score)
```

Repeated review rows are first averaged at the order level.

### Review target

- `Average Review >= 4.0 / 5` → target met
- `Average Review < 4.0 / 5` → warning

---

## 9. Freight Share

```text
Freight Share = Total Freight / (Total Revenue + Total Freight)
```

This measures the share of product-plus-shipping value associated with freight.

### Freight guardrail

- `Freight Share <= 15%` → within the project guardrail
- `Freight Share > 15%` → warning

---

# Additional Business Metrics

## Top Category Revenue Share

```text
Top Category Share = Revenue of highest-revenue category / Total Revenue
```

This measures how dependent the selected business view is on its leading product category.

## Top State Revenue Share

```text
Top State Share = Revenue of highest-revenue customer state / Total Revenue
```

## Top-Three Category Share

```text
Top 3 Category Share = Revenue of top 3 categories / Total Revenue
```

If the top three categories contribute more than 60% of revenue, the dashboard flags category concentration as a portfolio risk.

## Latest Monthly Revenue Growth

```text
Latest Growth = Latest Month Revenue / Previous Month Revenue - 1
```

Equivalent to:

```text
(Current Revenue - Previous Revenue) / Previous Revenue
```

## Repeat Customer Rate

The code first counts unique orders per `customer_unique_id`.

```text
Repeat Customer Rate = Customers with more than 1 order / Total unique customers
```

If the rate is below 10%, the dashboard generates a retention-focused recommendation.

## Average Late Delay

Calculated only for orders that are late:

```text
Late Delay = delivery_days - estimated_delivery_days
```

```text
Average Late Delay = MEAN(Late Delay)
```

If the average late delay exceeds 3 days, the dashboard generates an escalation recommendation.

## Review Gap Between On-Time and Late Orders

```text
Review Gap = Avg Review(On Time) - Avg Review(Late)
```

This measures the association between delivery outcome and customer review score.

A positive value means on-time orders receive higher reviews on average.

# Machine-Learning Objective

The ML model predicts:

> **Will this order be delivered late?**

Target:

```text
is_late
```

Classes:

```text
0 = On Time
1 = Late
```

The model is trained only on information available when the order is placed or promised, helping avoid target leakage.

---

## Model Features

### Numerical features

1. `total_sales`
2. `total_freight`
3. `item_count`
4. `estimated_delivery_days`
5. `purchase_month`

### Categorical features

1. `product_category`
2. `customer_state`
3. `seller_state`

Actual delivery outcome, actual delivery duration, review score, and `is_late` are not used as prediction inputs because those values are known only after the delivery outcome occurs.

---

# Preprocessing Pipeline

A single Scikit-learn pipeline handles preprocessing and classification.

## Numerical path

```text
Numeric Features
      ↓
Median Imputation
      ↓
Processed Numeric Features
```

Missing numerical values are filled with the median calculated from the training data.

Median imputation is robust to extreme values that can occur in variables such as product sales and freight.

## Categorical path

```text
Categorical Features
        ↓
Most-Frequent Imputation
        ↓
One-Hot Encoding
        ↓
Processed Categorical Features
```

Missing categories are filled with the most frequent training value. One-hot encoding then converts text categories into numerical indicator columns.

`handle_unknown="ignore"` allows the pipeline to receive a category at prediction time that was not present during training without failing.

---

# Random Forest Classifier

The estimator is a `RandomForestClassifier` configured with:

```text
n_estimators = 200
max_depth = 18
min_samples_leaf = 3
class_weight = balanced_subsample
n_jobs = -1
random_state = 42
```

### Why Random Forest?

A Random Forest combines predictions from many decision trees. It can model nonlinear relationships and interactions between numerical and categorical features after preprocessing.

### Why `balanced_subsample`?

Late orders may be less common than on-time orders. `balanced_subsample` adjusts class weights within each tree's training sample so the minority late-delivery class receives more attention.

---

# Train/Test Split

The dataset is split into:

```text
80% Training
20% Testing
```

Using:

```text
random_state = 42
stratify = y
```

Stratification preserves approximately the same late/on-time class ratio in both training and test data.

The model is fitted only on the training set and evaluated on the untouched test set.

---

# Model Evaluation Metrics

The training script reports several classification metrics because accuracy alone can be misleading when classes are imbalanced.

## Accuracy

```text
Accuracy = (TP + TN) / (TP + TN + FP + FN)
```

Overall percentage of correct predictions.

## Precision

```text
Precision = TP / (TP + FP)
```

Of the orders predicted as late, how many were actually late?

## Recall

```text
Recall = TP / (TP + FN)
```

Of all orders that were actually late, how many did the model detect?

## F1 Score

```text
F1 = 2 × (Precision × Recall) / (Precision + Recall)
```

Balances precision and recall.

## ROC-AUC

Measures how well the model ranks late orders above on-time orders across classification thresholds.

```text
0.5 ≈ random ranking
1.0 = perfect ranking
```

## Confusion Matrix

```text
                    Predicted
                 On Time   Late
Actual On Time      TN       FP
Actual Late         FN       TP
```

For delivery-risk prediction, false negatives are especially important because they are late orders the model failed to identify in advance.

# Model Persistence

Training happens in `train_model.py`.

The fitted pipeline — including preprocessing and the Random Forest — is saved as:

```text
model.pkl
```

The Streamlit application loads this saved model with `joblib` and does **not** retrain the model during prediction.

```text
train_model.py
      ↓
Prepare order-level data
      ↓
Fit preprocessing pipeline
      ↓
Train Random Forest
      ↓
Evaluate model
      ↓
Save model.pkl
      ↓
main.py loads model.pkl
      ↓
Predict Late / On Time
```

# Key Distinction: Business KPIs vs ML Metrics

These two groups measure different things.

## Business KPIs

Describe how the e-commerce operation is performing:

- Revenue
- Orders
- Average Order Value
- Freight
- Freight Share
- Average Delivery Time
- Late Rate
- Average Review
- Repeat Customer Rate

## ML Metrics

Describe how well the prediction model performs:

- Accuracy
- Precision
- Recall
- F1 Score
- ROC-AUC
- Confusion Matrix

A strong business KPI does not automatically mean the model is strong, and a strong model metric does not automatically mean the business itself is performing well.
